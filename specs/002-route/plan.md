# PLAN-ROUTE | v1.0 & v2.0 | from SPEC-ROUTE

## การตัดสินใจทางเทคนิค (`HOW` — `P-01` ถึง `P-07` ตรง)

### `P-01`: ค้นหา 2 ชั้น — `Redis Geo-Spatial` กรองเส้นตรงก่อน แล้วใช้ `Maps API` คำนวณระยะทางตามถนน
- **Traceability:** `<- REQ-FN-002, REQ-QA-002, Q-02 | MD-SEQ-04 ขั้น 6-7 (ขอระยะทางจาก Maps API)`
- **ชั้น 1:** `GEOSEARCH` ใน `Redis` หาคำขอ `"รอผู้รับงาน"` ในรัศมีเส้นตรง `5 กม.` (ค่า config `SEARCH_RADIUS_KM`)
- **ชั้น 2:** ส่งเฉพาะผลจากชั้น 1 ไป `Maps Distance API` แล้วตัดรายการที่ระยะทางตามถนนเกิน `5 กม.`
- **ทางเลือกที่ปฏิเสธ:**
  - คำนวณ `Haversine` ใน `RDBMS` หลัก (ช้า เสี่ยงเกิน 3 วินาที)
  - ส่งคำขอทุกรายการไป `Maps API` (ค่าใช้จ่ายสูงและช้า)

### `P-02`: รับงานด้วย `Conditional Update` แบบ Atomic + `Redis Lock` สั้น ๆ
- **Traceability:** `<- REQ-BR-002 (BR-02), Q-01`
- **การทำงาน:**
  ```sql
  UPDATE order SET status='มีผู้รับงานแล้ว', saleng_id=?
  WHERE order_id=? AND status='รอผู้รับงาน';
  ```
  ถ้าแก้ได้ `0 แถว` = เข้าเงื่อนไข `E2` (ซาเล้งอื่นรับงานไปก่อน)
- ลำดับตัดสินตามเวลาที่ request ถึง server (ค่าชั่วคราวของ `Q-01`) พร้อม `lock timeout 5 วินาที (config)`
- **ทางเลือกที่ปฏิเสธ:** `SELECT` แล้วค่อย `UPDATE` โดยไม่มีเงื่อนไขหรือ lock (เกิด race condition ซาเล้งสองคนได้งานเดียวกัน)

### `P-03`: ซ่อนพิกัดผู้ขายฝั่ง Server
- **Traceability:** `<- REQ-SEC-002, MD-DOM-04 (PII)`
- **การทำงาน:** API ค้นหาคืนค่าเฉพาะ `ตำบล/แขวง` และระยะทาง ส่วนพิกัดจริง (`geoPoint`, `addressText`) คืนค่าเฉพาะเมื่อ `order.saleng_id == ผู้เรียก`
- **ทางเลือกที่ปฏิเสธ:** ส่งพิกัดจริงให้ frontend แล้วซ่อนบนหน้าจอ (เพราะถูกดักข้อมูลจาก API ได้)

### `P-04`: ตรวจสถานะบัญชีซาเล้งก่อนกดรับงาน (`Guard`) โดยไม่สร้างระบบ `Thai-ID` ใน Feature นี้
- **Traceability:** `<- Precondition UC-04, SC-04, D-01`
- **การทำงาน:** อ่านฟิลด์ `saleng.verified` ที่ `UC-01` (ระบบยืนยันตัวตน) เป็นคนตั้งค่า
- **ทางเลือกที่ปฏิเสธ:** เชื่อมต่อ `Thai-ID / DBD-ID` ซ้ำใน `UC-04` (เป็นขอบเขตของ `UC-01`)

### `P-05`: แจ้งเตือนผู้ขายแบบ Asynchronous ผ่าน `Queue + Push Notification` พร้อม Retry
- **Traceability:** `<- UC-04 ขั้น 7, Q-05`
- **การทำงาน:** ส่งหลัง transaction รับงาน commit แล้วเท่านั้น (ป้องกันการแจ้งผิดเมื่อรับงานล้มเหลว ตาม Postcondition Failure)
- **ทางเลือกที่ปฏิเสธ:** เรียก push แบบ synchronous ใน request รับงาน (ทำให้การรับงานช้าลงหรือล้มเหลวตาม push service)

### `P-06`: จัดการเมื่อสัญญาณหรือบริการภายนอกขัดข้อง
- **Traceability:** `<- REQ-OP-001, E1, E3`
- **การทำงาน:**
  - `E1` (`GPS` ปิด): บล็อกการค้นหาและแจ้งให้เปิด `GPS`
  - ไม่มีอินเทอร์เน็ต: แสดง `cache` รายการล่าสุดพร้อมป้าย `"ข้อมูลอาจไม่อัปเดต"` และปิดปุ่มรับงาน
  - `E3` (`Maps API` ล่ม): `timeout 2 วินาที` แจ้งให้ลองใหม่ ไม่แสดงระยะทางที่ไม่ได้คำนวณจริง
- **ทางเลือกที่ปฏิเสธ:** ใช้ระยะทางเส้นตรงแทนเมื่อ Maps ล่ม (อาจคลาดเคลื่อนเกิน 15% ขัด `REQ-QA-002`)

### `P-07`: บันทึก `Audit Trail` ทุกครั้งที่กดรับงาน (สำเร็จและล้มเหลว)
- **Traceability:** `<- MD-ACT-04 "บันทึก Audit Trail Log (REQ-DAT)"`
- **ทางเลือกที่ปฏิเสธ:** ไม่บันทึก (ทำให้ตรวจสอบข้อพิพาท `"ใครรับงานก่อน"` ไม่ได้)
